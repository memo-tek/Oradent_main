# Oradent

نظام لإدارة عيادات الأسنان، يغطي بيانات المرضى والمواعيد والعلاج والفوترة والتأمين والتصوير والتقارير. المشروع مبني كـ monorepo بلغة TypeScript ويتكون أساسًا من تطبيق ويب وخادم API.

## بنية المشروع والتقنيات

- `packages/web`: واجهة Next.js 14 باستخدام App Router وReact وTypeScript. تستخدم TanStack Query لإدارة طلبات البيانات، وZustand لحالة التطبيق، إضافة إلى Tailwind CSS ومكونات Radix.
- `packages/server`: خادم Node.js وExpress وTypeScript. يستخدم Prisma للتعامل مع PostgreSQL، وZod للتحقق من المدخلات.
- `docker-compose.yml`: إعداد تشغيل PostgreSQL وRedis والخادم والواجهة محليًا.

## هل يدعم أكثر من عيادة؟

المخطط البرمجي يدعم عدة عيادات: يوجد جدول `Practice`، ويرتبط كل مقدم خدمة (`Provider`) بعيادة واحدة من خلال `practiceId`. وينشئ التسجيل عيادة جديدة ومالكًا لها. ترتبط إعدادات العيادة والكراسي وجدول الأسعار والمرضى مباشرةً بالعيادة، بينما تصل سجلات مثل المواعيد والعلاجات والفواتير والصور والمطالبات إليها عبر المريض أو مقدم الخدمة.

تفلتر كثير من استعلامات API البيانات باستخدام `practiceId` الموجود في رمز المستخدم، مباشرةً أو عبر العلاقات. لكن هذا النطاق لا يُطبّق بالطريقة نفسها في كل أجزاء المشروع؛ بعض المهام المجدولة، مثل تذكير المواعيد ومتابعة المطالبات، تستعلم عن السجلات دون تحديد عيادة في الاستعلام. لذلك فالتصميم متعدد العيادات، لكن عزل البيانات يحتاج مراجعة شاملة قبل اعتباره مكتملًا في جميع المسارات والمهام.

يمثل حساب الدخول سجل `Provider` واحدًا مرتبطًا بعيادة واحدة. البريد الإلكتروني فريد على مستوى النظام، ولا يبيّن المخطط علاقة تسمح للحساب نفسه بالانتماء إلى عدة عيادات.

## الأدوار والصلاحيات

الأدوار المعرفة في قاعدة البيانات:

- `OWNER` — مالك العيادة.
- `DENTIST` — طبيب أسنان.
- `HYGIENIST` — أخصائي صحة الفم والأسنان.
- `ASSISTANT` — مساعد.
- `FRONT_DESK` — موظف استقبال.

كل مسارات التطبيق المحمية تتطلب مصادقة. أما التفويض حسب الدور، فمحدود حاليًا: مسارات تعديل معلومات وإعدادات العيادة، وإضافة/تعديل الكراسي، وإضافة/تعديل مقدمي الخدمة وإعادة تعيين كلمات مرورهم تشترط دور `OWNER`. أغلب المسارات الأخرى لا تستخدم `authorize`، ولذلك لا تفرض تمييزًا إضافيًا بين الأدوار الخمسة، مع بقاء التحقق من المدخلات ونطاق البيانات المطبق داخل كل مسار.

## الموديولات الرئيسية

- **المرضى:** البحث عن المرضى وإدارة بياناتهم وحالتهم وسجلهم الطبي ومعلومات التأمين.
- **المواعيد:** عرض جدول المواعيد وإنشاؤها وتعديلها وحذفها وفحص التعارض.
- **المخطط السني واللثة:** تسجيل حالة الأسنان وقراءات اللثة.
- **العلاج والسجلات السريرية:** خطط العلاج وإجراءات العلاج المنفذة والملاحظات السريرية وتوقيعها.
- **الفوترة والمدفوعات:** الفواتير وتسجيل المدفوعات وكشف حساب المريض وجدول الأسعار.
- **التأمين:** المطالبات وحالاتها ومتابعتها.
- **التصوير:** رفع صور الأسنان والأشعة وعرضها وحفظ التعليقات التوضيحية.
- **الذكاء الاصطناعي:** تحليل الأشعة واقتراحات العلاج وتوليد الملاحظات وخطابات الموافقة المسبقة.
- **التقارير:** الإيرادات والإجراءات والأرصدة المتأخرة وإنتاجية مقدمي الخدمة والاستدعاءات ومؤشرات أخرى.
- **الإعدادات:** معلومات العيادة وساعات العمل والكراسي ومقدمو الخدمة.
- **سجل التدقيق:** تسجيل طلبات على مسارات حساسة مثل المرضى والعلاج والتصوير والفوترة، وربطها بالمستخدم والعملية والنتيجة.

## المصادقة وتدفق تسجيل الدخول

1. ترسل صفحة الدخول البريد الإلكتروني وكلمة المرور إلى `POST /api/auth/login`.
2. يبحث الخادم عن مقدم الخدمة، ويتأكد من أن الحساب نشط، ثم يقارن كلمة المرور بالتجزئة المخزنة باستخدام bcrypt.
3. عند النجاح، ينشئ الخادم Access Token وRefresh Token بصيغة JWT، ويضمّن بيانات مقدم الخدمة والعيادة والدور.
4. تحفظ الواجهة الرموز في `localStorage` وترسل Access Token في ترويسة `Authorization: Bearer ...` مع طلبات API.
5. يتحقق middleware `authenticate` من الرمز وصلاحيته، ويرفض رموز التحديث المستخدمة كرموز دخول والرموز الملغاة في Redis. ثم يضع بيانات الهوية في `req.auth`.
6. يطبّق middleware `authorize` قيد الدور على المسارات التي تستدعيه. عند انتهاء Access Token تحاول الواجهة تجديده باستخدام Refresh Token، وإلا تمسح بيانات الدخول وتعيد المستخدم إلى صفحة الدخول.

## المهام المجدولة والخدمات الخارجية

- **PostgreSQL وPrisma:** قاعدة البيانات ونماذج البيانات والعلاقات.
- **Redis:** تخزين قائمة الرموز الملغاة وبعض نتائج التخزين المؤقت.
- **التخزين المحلي للملفات:** تحفظ الصور المرفوعة على القرص وتُتاح عبر مسار `/uploads`؛ يخصص Docker volume للملفات.
- **Anthropic Claude:** خدمة اختيارية لوظائف الذكاء الاصطناعي، وتتطلب مفتاح API.
- **SMTP/Nodemailer:** خدمة إرسال البريد قابلة للضبط؛ في وضع التطوير يمكن تسجيل البريد بدل إرساله.
- **Socket.IO:** قناة تحديثات مباشرة بين الخادم والعملاء.
- **تذكيرات المواعيد:** مهمة كل ساعة تبحث عن المواعيد القريبة. الكود الحالي يسجل أنه سيرسل تذكيرًا ويحدّث حالة التذكير، لكن إرسال بريد أو SMS فعلي غير مطبق في هذه المهمة.
- **متابعة مطالبات التأمين:** مهمة يومية تحدد المطالبات القديمة وتعلّم الفواتير المتأخرة.
- **الملخص اليومي:** مهمة صباحية في أيام الأسبوع تحصي مواعيد اليوم والمطالبات والفواتير المتأخرة لكل عيادة وتسجل النتائج.

## التشغيل المحلي

```bash
# تشغيل PostgreSQL وRedis
npm run docker:up

# تطبيق migrations وإضافة بيانات تجريبية
npm run db:migrate
npm run db:seed

# تشغيل الواجهة والخادم
npm run dev
```

- الواجهة: `http://localhost:3000`
- الخادم: `http://localhost:4000`

## أمور غير مكتملة أو تحتاج انتباهًا

- صفحة استعادة كلمة المرور موجودة في الواجهة، لكن لا يوجد endpoint خلفي ينفذ الاستعادة.
- تذكير المواعيد لا يرسل بريدًا أو رسالة نصية فعلية بعد.
- بعض المهام والاستعلامات لا تقيّد البيانات صراحةً بـ`practiceId`؛ يجب مراجعتها للتحقق من عزل بيانات العيادات.
- التفويض حسب الأدوار مفصل فقط لعمليات المالك في الإعدادات؛ بقية المسارات لا تفرض صلاحيات منفصلة للأدوار الأخرى.

لمزيد من التفاصيل العملية عن كل دور وما تسمح به المسارات، راجع [ROLES_AR.md](./ROLES_AR.md).
